## 3. Question 2 — skew

### 3.1 Fresh requests (F), application behind by `s`, N = 2,000 per cell

| `s` | `login_protection` E-SAME / E-DOCKER | `otp_protection` | `custom_distributed` | ROT-F (LOGIN, E-SAME) |
| --- | --- | --- | --- | --- |
| 0.25 | 29.45 % / 31.45 % | 35.90 % / 30.95 % | 30.80 % / 30.80 % | 32.10 % |
| 0.50 | 55.45 % / 59.60 % | 56.00 % / 56.30 % | 59.75 % / 56.50 % | 59.65 % |
| 0.75 | 79.65 % / 80.45 % | 79.70 % / 81.85 % | 80.20 % / 80.40 % | 80.20 % |
| 1.00 | **100 % / 100 %** | **100 % / 100 %** | **100 % / 100 %** | **100 %** |
| 2.00 | **100 % / 100 %** | **100 % / 100 %** | **100 % / 100 %** | **100 %** |

(95 % intervals in `summary.md`; at 100 %, [99.808, 100].)

**Where in the second.** *(Computed for this report from the JSONL, all 18 sub-second cells, both environments.)* A fresh request throws iff the caller's sub-second fraction at L867 is ≥ 1 − `s`. The smallest throwing fraction and the largest non-throwing fraction straddle 1 − `s` within 2 ms in every cell; for example E-SAME LOGIN `s` = 0.25: 0.7499 / 0.7493. So as a share of **time**, the exposure is exactly `s`.

**Why the per-request rate exceeds `s`.** *(Computed for this report.)* A request that throws stops at the snapshot and is shorter: median time to the next request start 2.1 ms against 2.95 ms (E-SAME), 5.4 ms against 7.7 ms (E-DOCKER). A back-to-back loop therefore sends more requests per unit time during the throwing part of the second. The rate per request is a property of this loop, not of the code; the share of time is not.

### 3.2 Reused windows: the throwing period

For each repetition: `M0` = the Redis second in which the returned `expiresAt` was written (the creating request for R and ROT-R, the previous key for ROT-P). A request throws while its caller value is below `M0 + s`; after that the same window never throws again. Predicted and observed periods from the first request (E-SAME, median of 20 repetitions; full distributions in `summary.md`):

| `s` | R | ROT-R | ROT-P |
| --- | --- | --- | --- |
| 0.25 | 26.1 / 24.5 ms | 0 / 0 | 0 / 0 |
| 0.50 | 0 / 0 | 137.4 / 135.6 ms | 73.6 / 71.3 ms |
| 0.75 | 272.9 / 271.9 ms | 34.7 / 31.7 ms | 0 / 0 (3 repetitions throw, max 14.0 / 12.7 ms) |
| 1.00 | 145.6 / 144.8 ms | 784.7 / 783.9 ms | 723.4 / 722.5 ms |
| 2.00 | 1,666.5 / 1,665.3 ms | 1,307.9 / 1,307.3 ms | 1,234.1 / 1,231.0 ms |

(predicted / observed; the observed period ends at the last throwing request, so it is shorter by at most one request interval.)

**Correction to PLAN DV-3.** DV-3 said a reused window throws "during about `s` seconds after the key was created". Measured: it throws until the **caller's clock reaches `M0 + s`**, which is `s` minus the sub-second fraction of the creation, and can be zero for `s` < 1.

**The 20 repetitions are phase-locked.** Repetitions start about 5 s apart, so their creation fractions are nearly equal (E-SAME R at `s` = 0.50: `f0` 0.660–0.691). That is why R has 0 exceptions at `s` = 0.50 but some at 0.25 and 0.75. The rate of a reuse cell depends on the phase at which its repetitions happened to start; the law above (`M0 + s`) does not. V-3 = 100 % confirms the law on every request.

  * A fresh `checkOnly` runs five of them on `login_protection` and `otp_protection` and four on `custom_distributed` (`SYS` × F: 10,000 / 10,000 rows, except the two OTP rows that threw).

## 7. Question 4 — the exception reaches the Host

`host_surface.php`, `ALIGN-BEHIND1`, 100 fresh requests per policy, both environments (`expected/<env>/host-surface.txt`):

| Assertion | `login_protection` | `otp_protection` | `custom_distributed` |
| --- | --- | --- | --- |
| H-1 exactly `RateLimiterException`, validator message | PASS 100 / 100 (both envs) | PASS 100 / 100 | PASS 100 / 100 |
| H-2 failure signals emitted | 0 (both envs) | 0 | 0 |
| H-3 circuit state before = after | `null` = `null` (both envs) | same | same |
| H-4 `limit()` returned a result | 0 / 100 (both envs) | 0 / 100 | 0 / 100 |

By reading (§6.2 of the plan): `RateLimiterEngine::limit()` catches only `RateLimitConcurrencyException` (L336) and `BackendFailureException` (L348). So the exception skips `reportSuccess` (L333), is never reported as a backend failure, and gets no fallback decision. H-3 reads `null` because this path never writes circuit state; a reported failure would have written one.

## 9. The two environments, compared

* **Redis version:** 8.10.0 (E-SAME) and 7.0.15 (E-DOCKER). Every count that follows from the clock arm agrees between them:
  * 100 % at `s` ≥ 1;
  * the 1 − `s` threshold;
  * the detectors;
  * H-1 … H-4.
* **Timing:** E-DOCKER requests take about 2.5 × longer (79 s against 31 s for 10,000), and the `EVAL` round trip is about 2.5 × longer.
* **Clock offset:** E-DOCKER's `θ` moved from −4.6 ms to −0.3 ms during a 14-minute run, so its zero-skew count is not an estimate for a fixed offset.
* The numbers are reported side by side and never pooled.
