## Corrected boundaries

- **F300-01:** the entire advanced Pipeline claim enters `withinCall` before capability checks, registry reset, key derivation, the clock, or backend work. Legitimate owner nesting uses the existing coordinator admission, without changing its context/crossing rules. The entry audit also guards `isBackendHealthy`: the official store already guards itself, but a custom store may not. `process` was already guarded. `requestStore` and `ownedResources` are local inventory getters, perform no backend/Host callbacks and mutate no Pipeline request state. Construction captures immutable composition; it is not a processing entry. No other public Pipeline request entry exists.
- **F300-02:** independent known-device allowance migration now requires BudgetSeed on the actual captured account view before processing access. This check does not depend on `getBudgetConfig()`. It uses the command's failure intent, account/fingerprint presence, positive K5 delta, known-device trust/verification, configured previous outer secret, allowance interface and active allowance. The new getter is fetched through the existing guarded, per-call memoization; execution and retries use that value. When account/micro-cap budgets already require BudgetSeed, preflight adds no extra allowance callback.

Device-cap/active-block state cannot be read to prove the request will be ephemeral or already blocked before preflight; a potentially reachable allowance write must therefore be covered before those reads. The seven negative controls exercise no previous outer generation, unknown device, absent account, absent fingerprint, disabled allowance, zero K5 delta and precheck. Fingerprint-only rotation is a separate positive control: it creates a Current allowance without requiring account-allowance seeding. The existing account-budget and micro-cap conditions continue covering the other two `incrementBudgetAcrossRotation` call sites; only micro-cap identity can rotate with fingerprint material alone. The allowance's Previous auxiliary identity depends only on the outer secret. No protection policy, delta, allowance limit, key bytes or migration behavior changed.

**Builder boundary:** `KnownDeviceAccountAllowancePolicyInterface` declares an authentication policy. Builder's existing policy validation rejects `budget=null` (`Authentication policies require BudgetConfig`) without backend access. The new test proves this rejection unchanged; it does not advertise that configuration as a valid production policy or add a redundant Builder capability restriction. An advanced direct Pipeline accepts the policy object without Builder validation, so its preflight must still cover this reachable operation. Valid Builder authentication policies have a budget and are already covered by its existing previous-budget requirement. Read-only reader construction remains outside mutation preflight.
