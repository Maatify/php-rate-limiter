## 1. Scope

**Implemented.**

* `Service\AdmissionRuntime` (`@internal`, was the empty shell of 5-b1): `resolveLane()`, `reserve()`, `applyOutcome()`, the permit issue and claim, the fence read, `revokeAccountBinding()` (S8). Any failed lane check is **U**, never a refusal and never an exception (§4.1 "Credential verification").
* `RateLimiterEngine::limit()` in the §2.1 order: preflight → resolve device → fence → lane → pipeline (lane as a parameter, only for an opted policy) → reserve (ALLOW on `isPreCheck` only) → outcome hook (`isFailure | isSuccess`). `claimPostPunishmentReentry()` passes the lane only after the opt-in is verified (the 5-b3a constraint). The degraded and `FAIL_OPEN` paths do no admission, no lane and no epoch/fence read; `LocalFallbackLimiter` is untouched byte for byte.
* The refusal shape (S7): `SOFT_BLOCK`, `blockLevel` 1, `retryAfter` to the end of the refusing window or bucket refill, the six causes of §2.3 word for word, `scope` ∈ {`source`, `account`, `proof`, `device`}.
* The permit (S9, OD-1 = (b), required for opted policies only): issued on `ALLOW` in `RateLimitMetadataDTO::$permit`, claimed through `claimAdmissionPermit` on every outcome command. An outcome without a valid permit for an opted policy is **rejected and never re-sent as an unbound outcome** (AP §6.4). T0 stays for non-opted policies.
* S8: the engine implements `AdmissionBindingControlInterface::revokeAccountBinding()`; the composite runtime exposes it by `instanceof`, and the composite reader plus the public reader surface take the lane (deferred from D12 of 5-b3a).
* Dormancy stays: `RateLimiterBuilder::build()` does not construct an `AdmissionRuntime` (§1.1); DORMANT and REG are re-run. No preset declares S1.

**Not implemented here (named, ride 5-c):** DEC-026 `ACTIVE`, the one builder line, `DECISIONS_INDEX.md`, the amendments of the LOCKED contracts (`KS` §2, §3.4, §3.5, §4.6 status), DEC-022 `ACTIVE`, DEC-019's exit, the first opting policy, and the four findings `F-5b3a-LT9`, `F-5b3a-LT10a`, `F-5b3a-LT10b`, `F-5b3a-LT10c`.

**Prohibited here:** a DEC-025 constant or a `D` / `G` value in `src/` (the budgets and the permit timing arrive as constructor parameters of the runtime, §3 D-BUD, exactly as the 5-b2 store takes them as request parameters); an `if (false && …)` or other dead branch; an edit of any existing test; any touch of DEC-019, DEC-021, DEC-022, DEC-025 text or status.

## 2. Contract questions raised before the build (LT-12 …)

Each question names the contract text it comes from, what the build would do **if nobody answers**, and the executor's recommendation. LT-9 … LT-11 are 5-b3a's and are closed.

### LT-12 — Where the runtime gets the budgets (conflict inside the contract)

§0.1 L16: DEC-025 values "are package constants in 5-b, not Host-configurable". The assignment (and the 5-b3a rule) prohibits any DEC-025 constant in `src/` and says the budgets "arrive as request parameters as in 5-b2". Both cannot be built. **Recommendation:** an `@internal` value object `DTO\AdmissionBudgetsDTO` (W, `U_src`, `F`, `T`, `C`, `P_acct` window/day, `P_proof` window/day, `N_P`, D8 `F`, permit `D`, `G`, scope-key lifetimes) passed to `AdmissionRuntime`'s constructor; the **tests** build it from the values of §4; **5-c** builds it from package constants in the one builder line (the contract's "package constant" is then true at the builder, not inside the runtime). It is a shape outside S1–S9 (like `AdmissionLaneEnum`, LT-11) and joins the 5-c shape amendment. If not answered: this is built.

### LT-13 — The M2 fleet fence has no store operation and no input

L223 says the operator-set admission epoch is "checked in `reserve` and by the engine before a lane is resolved". The `reserve` contract (§2.4) has no fence input, and S1–S9 give no operator API. **Recommendation:** the fence is one integer in the existing epoch namespace, read with the existing `readBindingEpoch(fenceKey, null)` (so no new store operation, no edit of the 5-b2 stores); the new path is **enabled for a budget group iff the integer is ≥ 1**; the key derivation is a new reserved purpose `admission_fence` (a `KS` §4.6 addition that rides 5-c with the other purposes). The operator sets it with the store's existing `bumpBindingEpoch` (harness and runbook), and **5-b3b ships no public operator method** (a package-owned way to set it is a 5-c decision). The check happens before any lane resolution; a fence below 1 means the request is processed exactly as an engine without an admission runtime would (S0 byte for byte, no reserve, no lane). If not answered: this is built.

### LT-14 — How an outcome finds the window and the lane of its admission

The reservation keys carry the window (`W`) and day index of the **admission** time. An outcome arrives later (`D` seconds later at most for a valid permit): a refund or a net-set removal derived from the **outcome's** clock can hit another window's key (a refund into a fresh window decrements someone else's unit). The permit record in 5-b2 stores `lane`, `subject`, `operation`, `deadline`, `grace` and no admission time; the claim returns an enum only. The lane at the outcome must also equal the lane at the admission (the credential may expire in between). **Recommendation:** the permit token handed to the Host is `base64url(json{v, id, lane, t0}) . '.' . base64url(HMAC(domain, payload))` signed with the binding key (the codec's key, a separate domain string, current and previous like the credential). The runtime verifies the MAC before any store call, takes `lane` and `t0` from it, and derives the outcome's scope keys from `t0` (window, day) and `lane`; `operation` = the policy name and `subject` = the admission subject are sent to `claimAdmissionPermit`, so a wrong account / policy / lane is `REJECTED` by the store. The store id is the token's `id`. A token whose MAC fails is `unknown`-class (never reaches the store). Without this the refund and the net-set removal are wrong at every window boundary, so it is a build input, not an optimisation. The Host model passes the same context at the outcome as at the admission (a USAGE_GUIDE duty: the outcome's IP selects the source set; the Host, not the client, makes outcome calls).

### LT-15 — What an expired permit does (the NM-10 mechanism may have no effect)

§3 (b) says "the same expiry rule applies **per permit**" as (a) ("an admission with no outcome by `D` counts as a failure"). SF §2.3 says the opposite: `EXPIRED` is a tombstone, "a lost or late outcome costs one scoring; it never changes an admission bound". The 5-b2 store has **no operation that applies an expired permit as a failure** (nothing runs at the deadline; `applyAdmissionOutcome` fires on an outcome event). So with the store as built, a Host that drops an outcome leaves the net failure set `F` and the D8 set unchanged, whether or not it sends permits: the permit binds outcomes that **arrive**, it does nothing for outcomes that **do not**. Then NM-10's gate (A3 holds at the highest drop share) fails with the mechanism as it fails without it, and the detector ("without the mechanism it fails A3") cannot separate the two arms. Options:

| | Mechanism | Cost |
| --- | --- | --- |
| **(1)** build as the contract's store defines it; measure NM-10 as it is and report the result (expected: A3 fails at the highest share with and without the mechanism, so the detector does not discriminate and the gate is "not evidenced"/FAIL) | none | NM-10 is registered in DEC-024 point 3 as a gate **before merge**: an honest FAIL blocks the merge by the Owner's own rule |
| **(2)** presumption of failure at reserve on the **U door only**: after an admitted U reservation the runtime calls the existing `applyAdmissionOutcome(FAILURE)` for the net set `F` (scope `SET_SIZE`, member = the subject); a recorded `SUCCESS` (existing op) removes it. A dropped outcome therefore stays a failure for `F`; no new store operation | a second store call after the reserve (not atomic with it; a typed failure between them leaves a spent unit and no set entry: the safe direction); no effect on the D8 set (P), by design, because D8 neither adds nor removes on success (`D-PXALL` counting every outcome is the registered detector that refuses 32/61 of `N12T`); `ρ` > 1 probes become failures on the U net set (what NM-5 measures) |
| **(3)** a new store operation that settles expired permits lazily at the next reserve of the same source | a 5-b2 contract change (new Lua, new NM-6 fixtures) | outside this PR's scope |

**Recommendation:** (2), because it is the only option that needs no new store operation and gives the A-2 declaration an effect on the U door, with the P/D8 limit stated; if the Lead prefers (1), NM-10 is reported as measured and the merge is blocked by it; (3) needs its own PR before 5-b3b. **The NM-10 and NM-5 gates cannot be registered with a PASS condition until this is answered**, so §5 registers them for both readings and the test commit waits.

### LT-16 — Result shape of an outcome the permit did not accept

SF §2.3 lists `duplicate`, `conflict`, `rejected`, `late`, `unknown`; the contract adds "an outcome without a valid permit is rejected". `recordFailure` / `recordSuccess` return a `RateLimitResultDTO`; nothing says what an unaccepted outcome returns, and it must be distinguishable by the Host. **Recommendation:** no scoring, no exception (an exception in a Host's failure path is a worse failure than a metric), a `RateLimitResultDTO` with `ALLOW`, `blockLevel` 0, `retryAfter` 0 and `metadata->cause` ∈ {`permit_missing`, `permit_duplicate`, `permit_conflict`, `permit_rejected`, `permit_late`, `permit_unknown`}, `context->scope` = `permit`. Seven new `cause` values on S7; `accepted` is the normal result. `permit_missing` covers an opted policy's outcome with no permit (and a token whose MAC fails is `permit_unknown`). If not answered: this is built.

### LT-17 — SC-3 and the pipeline's pre-check writes before a refusal

§2.1 runs the pipeline (which writes the `checkOnly` observation state, C-c2) and **then** reserves; SC-3 says a capacity refusal causes "no score, budget, watcher or cycle change". They agree only if SC-3 is read as **K4/K5 scores, the 24 h budget, Anti-Equilibrium watchers and block cycles**; the pre-check observation writes (device-cap and flood bookkeeping on U, the K1/K2 observation scores) have already happened when the reserve refuses. **Recommendation:** read SC-3 that way; the gate asserts the four listed state classes unchanged across a refusal and **reports** the observation writes. If SC-3 must also cover observations, the reserve has to move before the pipeline's writes, which contradicts §2.1 (AP §6.2: read penalties, then reserve) and is a contract change.

### LT-18 — One source derivation, two users

The source of §2.2 is "IPv4 exact or IPv6 /64 (the K1 prefix function `EvaluationPipeline::getIpPrefix`)", a **private** method. **Recommendation:** extract the body to an `@internal` static helper and make `getIpPrefix` delegate to it (no behaviour change; S0-PARITY and the 5-b3a goldens prove it). This edits an existing source file, never a test. If not answered: this is built.

### LT-19 — The subject of the credential, the bucket and the epoch

LT-4 fixes the admission subject (bucket, sets) = `correlationId ?? accountId`. The credential's `subject` claim is verified against a subject; the epoch (S8) is per **account**. **Recommendation:** the credential subject is the **admission subject** (so the codec check and the reservation agree); the epoch key is derived from `accountId` (S8 takes an account id); a request with no `accountId` can never be P (no epoch to read). A request with no subject at all reserves only the source scope (LT-4: "without a subject, `U_acct` and the sets do not apply"). If not answered: this is built.
