## 1. Scope

**Implemented.** `EvaluationPipeline::process()` and `claimPostPunishmentReentry()` take an optional last parameter, the lane (`null` = today, byte for byte). The lane is a call parameter, never object state (§2.1, LT-7). With a non-null lane the pipeline applies, as explicit rules, the study guards of the opted policy (§2.2 rows "K1 / K2 / K3 off", "U lane", "K4P", "P-family device state", "K5 material"). `RateLimitOperationalReader` follows the same material and family selection through an optional lane on its concrete `read()`.

**Nothing in production passes a non-null lane in this PR.** `RateLimiterEngine` is not edited, `RateLimiterBuilder::build()` is not edited, no policy can opt in (M1, dormant).

**Not implemented here (named, deferred to 5-b3b, §10):** `AdmissionRuntime` (it stays the empty shell of 5-b1), lane resolution from a credential, the reservation call and its refusal shape, the permit, outcome hooks, `AdmissionBindingControlInterface` implementation, the engine passing a lane, the builder line, `CompositeRateLimitOperationalReader` and the public reader interface asking for a lane, `docs/DECISION_MATRIX.md`, `docs/POLICIES.md`, `docs/guides/USAGE_GUIDE.md`, `docs/FAILURE_SEMANTICS.md`, DEC-026 and every record under `docs/decisions/`. Gates deferred with them: RP-G4, RP-G6, RP-G7, RP-GLOB, FAIL, SC-1…6, NM-5, NM-7 (mixed fleet, rollback), NM-10, LANE, and the RP-G5 parts that need a reservation: `UAX-NP`, `D-IDMINT`, `BRU24`, `FORGE`, `MINT`, `STEAL`, `NP-IN`, `R:STEAL`, `R:STREAMS` (they need `N_P`, the U/P admission counters, the credential or the password-change binding, none of which exist before 5-b3b).

**Prohibited here:** any DEC-025 constant in `src/` (a window, a cap, a threshold, a TTL value specific to admission), any `if (false && …)` or other dead branch, any edit of an existing test, any edit of `FingerprintHasher` (LT-8), any touch of DEC-019 / DEC-021, any decision record or index line.

## 2. The question that had to be settled first: which key is the "previous" K5 key under M4 / M5

The pipeline derives every K5-family key twice: a current one and, when a previous generation exists, a previous one that is **read-only** (and never `max(v1, v2)`, DFP §5.1.6). For a device that carries an instance id there are two things that can be called "previous": (A) the **same material** under the **previous secret**, or (B) the **fingerprint material** (the old K5 key of the device) during a K5-material transition window.

**What the contract says, with the lines.**

| Reading | Where the contract supports it |
| --- | --- |
| **A, same material, previous secret** | L111 (§2.2, K5 material row): the id component is hashed "by the current and (if present) the previous `FingerprintHasher`" and "two generations come from the existing current/previous pair"; the pipeline "selects between components and never re-hashes". L190 (§4.2): DEC-003 point 7 "applies only across **secret** generations, **not** across material generations". L225 (M4), first sentence: the id switch is "a **one-time K5 restart** for exactly those devices". L226 (M5): without the non-overlap rule the pipeline would read the Cartesian combination that DFP §5.1.6 forbids. The archived study (`g5-k5-id-material.diff`, `g5PreviousK5Material`) is reading A |
| **B, fingerprint as the previous generation** | L225 (M4), second sentence: "The K5 material migration reads the old material as the 'previous' derivation during a **transition window ≥ the longest K5-family lifetime** and writes only the new key" |

**Finding (raised, not built on).** The same M4 row says both "a one-time K5 restart" (the old state is **not** carried: A) and "reads the old material as the previous derivation" (the old state **is** read: B). L190 says the material change is "a restart, not a merge", which is A. And reading B has no input in the contract: nothing in S1–S9 or in §1 tells the pipeline that a transition window is open, when it ends, or what its length is (the length is a "longest K5-family lifetime", a value no decision states); M5 makes the two readings never overlap in time but does not say who selects between them. I therefore raise it as **LT-9 for the Lead** and build **only the part that is identical under both readings and is required by the registered gates**: reading A (it is what the study measured, what the RP-G5 numbers and the READER-PARITY gate are defined on, and what L111 / L190 / the first sentence of M4 describe). Reading B is **not implemented**. `previousK5Material()` is the single seam where B would be added, additively, once the Lead states its input (a window flag or a config value) and its length. Until then a device that starts sending an id restarts its K5 (the declared one-time cost of M4), which is the safe direction (it can only forget, never carry the wrong state).

**LT-9 asked of the Lead:** A (as built) or B? If B, which input opens the window and what is its length?

## 4. Seams (named private helpers of `EvaluationPipeline`) and the mutation detectors

A detector in this PR is **a mutation of the real `src/` file**, not a second implementation: a test helper (`tests/Support/Admission/PipelineMutant`) reads `src/Service/EvaluationPipeline.php`, replaces **one named method body** (or one exact line) and loads the result as a differently named class in the same namespace. The helper fails if the anchor is not found exactly once, so a detector cannot silently stop mutating. The helpers below are the registered seams; their names are part of this plan.

| Seam | Meaning | Mutation (detector) |
| --- | --- | --- |
| `k4KeyType(?AdmissionLaneEnum)` | `'k4p'` on P, else `'k4'` | return `'k4'` (K4P merged into K4) → CYCLES, LIFECYCLE |
| `k5KeyType(?AdmissionLaneEnum)` | `'k5p'` on P, else `'k5'` | return `'k5'` → CYCLES, RP-G5 |
| `laneAuxiliaryPurpose(?AdmissionLaneEnum, string)` | purpose with `_p` on P | return the unsuffixed purpose → RP-G5 (allowance counter shared) |
| `k5Material(DeviceIdentityDTO, ?AdmissionLaneEnum)` | id component, else fingerprint; `null` lane = fingerprint | (a) return `fingerprintHash` for every lane → UAX fails (material detector); (b) ignore the lane, always id → S0-PARITY fails |
| `previousK5Material(DeviceIdentityDTO, ?AdmissionLaneEnum)` | previous generation of the material | return the current material → READER-PARITY and rotation rows |
| `appliesCollectiveCorrelation(?AdmissionLaneEnum)` | `true` only for `null` | return `true` → GUARDS (collective block appears on U and P) |
| `isProvenLane(?AdmissionLaneEnum)` | `true` only for `P` | return `false` → GUARDS (device-cap, flood, K1–K3 on P) |
| `keepsDeviceScopeOnly(?AdmissionLaneEnum)` | `true` only for `U` | return `false` → GUARDS (an account block persists on U) |
| `reentryEvidenceLane(?AdmissionLaneEnum)` | the lane whose K4 key the evidence is read from | return `P` → LIFECYCLE (K4P evidence shown on U) |
| the four G5 ablations, as **exact-line** mutations of today's lines | `($allowanceLimit = null) !== null` (no allowance), `$result['k5'] = 0;` (no K5), the K4 overflow assignment removed, `deviceAntiEquilibriumKeys` returning `null` | the archived ablation outputs (`g5v2_pipeline.G5V2-NOALW/NOK5/NOOVF/NOAE.jsonl`) are the expected results of the mutants |
