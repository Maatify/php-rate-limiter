الخلاصة: لا يمكن تحقيق “لا حجب للأبرياء خلف NAT” و“لا تجاوز للمهاجم الذي يقلّدهم ويدوّر هويات رخيصة” معًا من الإشارات الحالية وحدها. الحل الصحيح ليس تغيير Thresholds، بل نقل النظام من Rate Limiting مبني على “هوية مفترضة” إلى Admission Control هرمي، مع كلفة أو إثبات إضافي عند الاشتباه.

## 1. Root Cause Analysis

المشكلة الأساسية هي خلط السمات بالهوية الأمنية:

| المشكلة | لماذا هي أساسية |
|---|---|
| IP وUA وFingerprint وCookie ليست هوية موثوقة | قد يشترك الأبرياء فيها، أو يدوّرها المهاجم |
| الحصة المشتركة بلا Fair-Share | يستطيع طرف واحد استنزافها وتعطيل الجميع |
| الحصص الفردية بلا حصة أب | يستطيع المهاجم إنشاء هويات كثيرة والحصول على سعة غير محدودة |
| الحجب على مستوى Network | يحوّل نشاط شخص واحد إلى عقوبة جماعية |
| الاعتماد على Outcomes | لا يمنع وصول الدفعة المتزامنة إلى الـVerifier قبل تسجيل النتيجة |
| فحص ثم زيادة غير ذري | لا يضمن حدًا فعليًا تحت التزامن |

أما K1–K5 فهي ليست خاطئة بحد ذاتها، لكن جعل نطاقاتها مصدر قرار حجب جماعي هو موضع الخلل. مثلًا، `IP + Browser Major` لا يمثل مستخدمًا ولا جهازًا، لذلك تدوير Browser Major يجزّئ الحارس المشترك، بينما تشابه المتصفحات الشرعية قد ينتج حجبًا كاذبًا.

## 2. Feasibility Boundaries

يمكن ضمان الآتي:

- حد أعلى للمحاولات التي تصل إلى الـVerifier، إذا كان الحجز قبل التحقق وذريًا.
- حماية Account عبر الشبكات المختلفة.
- منع Cookie أو Client ID جديد من منح حصة مستقلة.
- تقليل قدرة طرف واحد على احتكار Network Budget.
- استبدال حجب الشبكة المباشر بـChallenge أو تأخير متدرج.
- عمل حماية pre-auth حتى عند غياب Outcomes، لكن بدقة أقل.

لا يمكن ضمان الآتي:

- التفريق الحتمي بين مهاجم ومستخدم بريء إذا قدّما نفس الإشارات، في التوقيت نفسه، وبالكلفة نفسها.
- عدم طلب Challenge أبدًا من مستخدم جديد داخل شبكة تتعرض لهجوم.
- Fair-Share حقيقية لكل “إنسان” اعتمادًا على Cookie أو CIT مجاني الإنشاء.
- منع Spray واسع موزع على آلاف الشبكات بلا إشارات خارجية أو كلفة إضافية.

برهان الحدّ: إذا كان قرار النظام هو `f(observation)`، واستطاع المهاجم إنتاج observation مطابقة للمستخدم البريء، فسيأخذ القرار نفسه. العشوائية تغيّر الاحتمال فقط؛ لا تنتج معلومة أمنية جديدة.

إذًا Client Instance Token الموقّع يثبت أن الـHost أصدر الرمز، لا أنه يمثل إنسانًا فريدًا أو حسن النية.

## 3. Alternative Designs

| التصميم | النتيجة |
|---|---|
| تحسين K1–K5 والـThresholds | يحسن حالة ويكسر أخرى؛ لا يعالج Sybil أو Fair-Share |
| Account-centric مع إعفاء الجهاز/الجلسة المعروفة | جيد لحماية حساب واحد، لكنه يفتح Spray عبر حسابات وجلسات صحيحة |
| Device/Client quota مستقلة | تفصل متصفحات NAT، لكنها تصبح تجاوزًا غير محدود إن كان إنشاء الهوية رخيصًا |
| هوية مادية أو مزود Risk خارجي | قد يعطي إشارة أقوى، لكنه ليس عامًا لمكتبة PHP مستقلة ويزيد التكلفة والاعتمادية |
| Admission Control هرمي + CIT كـSub-Key + Challenge | الأفضل، بشرط أن CIT لا يصبح امتيازًا ولا حصة مستقلة |

التصميم الثالث لا يصبح مقبولًا إلا إذا كانت عملية إصدار الهوية نفسها محدودة أو مكلفة: Device Attestation مناسب لبعض تطبيقات الهاتف، لكنه ليس بديلاً عامًا للويب.

## 4. Recommended Architecture

أوصي بـ **Hierarchical Costed Admission Control**.

كل محاولة تحجز سعة قبل الوصول إلى الـVerifier من هذه النطاقات:

- `Global(operation)`: سقف حماية الخدمة.
- `Network(prefix)`: رصد وإدارة السعة المشتركة عبر الحسابات.
- `Account`: حماية الحساب حتى إذا تغيّر IP.
- `Account + Client Instance`: منع تكرار المحاولة من العلاقة نفسها.
- `Client Instance`: حدّ سلوكي فرعي، وليس Budget مستقلًا.
- `New/Unattested Client Pool`: حصة مشتركة صغيرة لكل الهويات الجديدة داخل الشبكة.

المبدأ الحاسم: كل Client Instance يظل تابعًا لحصة Network وGlobal. لا يوجد مسار تصبح فيه Cookie جديدة = سعة جديدة.

عند ضغط Network:

1. لا تُصدر `DENY` جماعيًا لمجرد ظهور حسابات أو بصمات متعددة.
2. يتحول النطاق إلى `CONSTRAINED`.
3. الهويات الجديدة تدخل حصة Probation مشتركة ومحدودة.
4. العميل الذي يتجاوز حصته الفرعية يُطلب منه `CHALLENGE` أو يحصل على `THROTTLE`.
5. اكتمال Challenge ينتج Admission Ticket محدودًا، ثم يعاد الحجز؛ لا يتحول مباشرة إلى إعفاء.
6. `DENY` يبقى للحساب المستنزف، أو السقف العالمي، أو عندما لا توجد سعة حقيقية.

يُستخدم CIT في:

- فصل سجل الاستهلاك بين متصفحين خلف NAT.
- حفظ تاريخ قصير المدى.
- تحديد Client Sub-Key.
- تقليل الاحتكاك تدريجيًا.

ولا يُستخدم في:

- منح حصة مستقلة.
- تجاوز Network أو Global.
- مسح Failure Debt.
- منح إعفاء بسبب نجاح سابق أو Session موثوقة.

الـOutcomes تعدّل فقط دينًا محليًا محدودًا للحساب أو العلاقة `Account + Client`. نجاح واحد لا يعيد Network أو Global Budget، ولا يمحو دلائل Spray عبر حسابات أخرى.

### الذرية

يجب أن يكون `reserve()` قبل الـVerifier، مع `attempt_id` فريد، وأن يحجز كل القيود المطلوبة دفعة واحدة.

Lua في Redis ذرية داخل العقدة أو الـhash slot نفسها فقط؛ ليست معاملة موزعة تلقائيًا. لذلك لا يجوز الادعاء بأن Redis Cluster يحقق عملية ذرية تشمل Global وNetwork وAccount مفاتيح موزعة على slots مختلفة.

لضمان قوي، يلزم واحد من الآتي:

- Redis primary واحد أو admission coordinator واحد لكل عملية محمية.
- مخزن يقدّم معاملة ذرية فعلية.
- تقسيم مسبق محافظ للسعات إلى leases؛ لكن هذا يضعف الاستغلال الكامل للسعة ويجب توثيقه كضمان مختلف.

الحجز التسلسلي عبر عدة مفاتيح قد يحافظ على سقوف منفردة، لكنه يخلق حجوزات مهدرة يمكن استغلالها لتقليل الإتاحة؛ لا أعتمده أساسًا للـFair-Share.

## 5. Threat-Model Walkthrough

| السيناريو | ما يصل إلى الـVerifier | الضرر الجانبي |
|---|---|---|
| 100 موظف خلف NAT | المحاولات التي تحجز Network وClient وAccount؛ المهاجم لا يحتكر Network وحده | العميل الجديد قد يواجه Challenge عند الضغط |
| مستخدمان بنفس IP وUA | لكل CIT أو Account+Client سلوك منفصل؛ المكرر يستهلك حصته فقط | بدون CIT موثوق قد يتشاركان Probation Pool |
| مستخدم جديد بلا Cookie | حصة أولية صغيرة؛ ثم Challenge عند ضغط الشبكة | الاحتكاك متعمد ومحدود |
| مستخدم يخطئ مرتين ثم ينجح | المحاولات ضمن Account limit؛ النجاح يخفف دينه المحلي فقط | لا يسترد Network/Global consumption |
| 200 حساب خاطئ | Network sees aggregate distinct-account pressure؛ فقط السعة المحجوزة تمر | لا يجوز تحويل HLL التقريبي وحده إلى Hard Deny |
| مهاجم يملك 12 جلسة صحيحة | لا تحصل جلساته على bypass؛ تبقى تحت Global/Network/Account | قد يمر جزء محدود، وهذا ثمن تجنب الحجب الجماعي |
| تدوير UA وBrowser وCookie | الهويات الجديدة تشترك في New Pool؛ لا تعيد Budget الأب | قد يرفع Challenge rate للمجهولين |
| مهاجم داخل مكتب شرعي | Fair-Share يقلل احتكاره، ولا يثبت أنه إنسان مختلف | لا توجد حماية مطلقة إن استطاع اجتياز Challenges بكلفة مقبولة |
| 100 طلب متزامن | فقط الحجوزات الذرية ضمن السعة تمر | لا توجد نافذة “تمر أولًا ثم نسجل لاحقًا” |
| Host بلا Outcomes | الحجز pre-auth يظل قائمًا؛ لا reputation ولا refund | سياسة أكثر تحفظًا للمستخدم الشرعي |

لا أضع أرقامًا للمحاولات المسموحة هنا؛ تلك مقايضة منتج يجب قياسها واعتمادها، لا رقمًا معماريًا مفترضًا.

## 6. Security vs Availability Trade-offs

المكاسب:

- لا يصبح IP وحده سببًا لحجب مكتب كامل.
- لا ينتج عن تدوير الهوية حصص لا نهائية.
- تبقى حماية Account قائمة عند تغيير الشبكات.
- تقل قدرة Session أو نجاح قديم على تنظيف نشاط هجومي جديد.
- يوجد سقف فعلي قبل الـVerifier.

الخسائر:

- المستخدم الجديد يتحمل Challenge أكثر عند ضغط الشبكة.
- Challenge نفسها ليست سحرية: CAPTCHA أو PoW ترفع كلفة المهاجم ولا تثبت براءته.
- المهاجم الذي يملك حسابات أو CITs كثيرة قد يحصل على عدة حصص فرعية، ما لم تكن الإصدار والتحديات مكلفة ومحدودة.
- Redis/coordinator يصبح جزءًا من مسار حماية حساس.
- لا يحل التصميم Botnet موزعًا على نطاق واسع دون مصدر Risk خارجي.

## 7. Host Integration Contract

الحد الأدنى المقترح:

```text
reserve(operation, account?, network, client_instance_token?, signals?)
  -> { decision, attempt_id?, retry_after?, challenge? }

settle(attempt_id, outcome)
  -> void

issue_client_instance_token()
validate_client_instance_token(token)
```

شروط العقد:

- يستدعي الـHost `reserve()` قبل Password/OTP Verifier.
- `THROTTLE` لا يعني “مرر الطلب بعد sleep”؛ يعاد الحجز عند انقضاء التأخير.
- `settle()` اختياري، لكنه لا يغيّر حدود pre-auth.
- CIT عشوائي، موقّع، مقيّد العمر، ومعرّف بإصدار مفتاح.
- إصدار أو ترقية CIT يجب أن يستهلك من Issuance Budget أو يتطلب Challenge عند الضغط.
- لا تُخزن PII خامًا: استخدم HMAC versioned لـAccount، Network، وCIT ID.
- لا تثق برأس IP غير موثوق؛ يجب أن يأتي Network من trusted proxy contract.
- Challenge adapter من مسؤولية الـHost؛ المكتبة تطلبه ولا تنفذه.

في Login وOTP، Redis outage يجب أن ينتهي بسياسة صريحة، غالبًا Fail-Closed أو Challenge-only. Local per-worker bucket قد يقلل الضرر، لكنه لا يحقق ضمانًا موزعًا ويجب ألا يُسوّق كذلك.

## 8. Validation Strategy

اختبر قبل التنفيذ، وبسيناريوهات مستقلة ذات traffic traces ثابتة:

- NAT شرعي مع مهاجم داخلي.
- 200 حساب مختلف، ثم تدوير CIT وUA وFingerprint.
- مهاجم يمتلك 2 و12 و50 حسابًا وجلسات صحيحة.
- مستخدمون جدد، LOW fingerprint، وفقدان Cookie.
- دفعات متزامنة أكبر من أي Budget.
- غياب Outcomes، Outcomes مكررة، وOutcome متأخر.
- Redis restart، timeout، network partition، version skew، rollback، وkey rotation.
- IPv4 وIPv6 prefixes المختلفة.

المقاييس:

- عدد المحاولات التي بلغت الـVerifier لكل campaign مهاجم.
- نسبة Allow/Challenge/Deny للمستخدمين الشرعيين بحسب فئة الثقة.
- نسبة Network Budget التي يلتهمها أكبر Client.
- المكسب الهامشي من كل CIT جديد.
- عدد خروقات حدود الحجز الذري: يجب أن يساوي صفرًا.
- Redis p99، حجم المفاتيح، وTTL behavior.
- معدل اكتمال Challenge والانقطاع بعدها.

أرفض التصميم إذا أثبتت التجارب أيًا من الآتي:

- CIT جديد يرفع سعة المهاجم بلا حد.
- عميل واحد يلتهم Network Budget رغم Fair-Share.
- نجاح حساب واحد يمحو أثر Spray عبر حسابات أخرى.
- Redis Cluster يخرق ذرية القيود المركبة.
- outage يفتح مسارًا غير محدود إلى الـVerifier.
- Challenge يتحول عمليًا إلى منع غير مقبول تجاريًا للمستخدمين الجدد.

## 9. Outstanding Questions

- هل يمكن للـHost تقديم CIT موقّع ومحدود الإصدار؟
- ما Challenge المتاح فعليًا، وما كلفة تجاوزه؟
- هل Redis هو single primary أم Cluster متعدد slots؟
- ما سلوك Login وOTP عند فقد Redis؟
- ما مصدر IP الموثوق وسياسة IPv6 (`/64` أم غيره)؟
- هل يسمح الإطار القانوني باستخدام Cookie/Installation ID؟
- ما نسبة Challenge المقبولة تجاريًا للمستخدم الجديد؟
- هل threat model يشمل Botnet متعدد IPs؟ إن كان نعم، فالمكتبة وحدها غير كافية.

## 10. Final Verdict

أوصي بالتصميم المقترح، لكن ليس قبل حسم ثلاثة شروط:

1. اختيار مسار ذرية حقيقي للـAdmission Control، وعدم افتراض أن Lua تحل معاملات Redis Cluster الموزعة.
2. اعتماد CIT كـSub-Key فقط، مع Issuance Budget وProbation وChallenge؛ وليس كامتياز أو quota مستقلة.
3. اعتماد منتج صريح لمقايضة Challenge مقابل المحاولات الإضافية التي قد يصل بها المهاجم إلى الـVerifier.

إن لم تتوفر هذه الشروط، فالقرار الصادق هو سياسة أكثر تحفظًا مع ضرر NAT معروف ومعلن؛ وليس Fair-Share ظاهرية يمكن للمهاجم تجاوزها عبر تدوير الهوية.
